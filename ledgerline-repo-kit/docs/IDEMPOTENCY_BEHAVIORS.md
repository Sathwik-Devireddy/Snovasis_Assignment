# IDEMPOTENCY_BEHAVIORS.md — Behaviour table from D-8 (P2.4)

- **Phase:** 2 · **Date:** 2026-11-06 · **Status:** Draft for Gate 2 review
- Scope of a key: unique on `(actor_id, operation, idempotency_key)`. Same key from another user = a different key (IDEM-004).
- Client contract: send an opaque key (≤64 chars) per *user-intent*, not per click; keep the **same key** when retrying for any reason (timeout, disconnect, unknown outcome). Never a new key while unsure — that is how money doubles (T-030).
- Honest claim wording everywhere: **"at most one financial effect per scoped key, with replay of the stored outcome"** — never "exactly once end-to-end".
- Canonical conflict rule (approved): **same scoped key + different canonical payload → `409 KEY_REUSED`** — the *only* conflict code. Same key + same payload replays the stored result (including concurrent in-flight duplicates, row 6, and previously refused attempts, row 2) — but only **after the replay re-evaluation gate passes** (row 7): session validity → **401 `UNAUTHENTICATED`** (a revoked session never gets a stored response, and never a 404 for the revocation), grant/account visibility → the single uniform **404 `ACCOUNT_NOT_FOUND`** envelope, and involved-account status still `ACTIVE` → otherwise **409 `ACCOUNT_NOT_ACTIVE`**. The gate is an evaluation-only pass with no writes and no new attempt rows (`REFUSAL_CODES.md` §3); the no-new-rows guarantee covers the gate pass and post-claim refusals — a replay refused **pre-claim** at step 1b records the ordinary D-9 authorisation-refusal row (key-state-independent: one insert attempted per refused call, exactly one durable row when persistence succeeds; REPLAY-AUTHZ-001).

## Behaviour table

| # | Scenario | Caller receives | Financial effect | Stored data / notes |
|---|---|---|---|---|
| 1 | **New key, success** | 200/201 outcome | One journal, balances updated | Idempotency row created inside the transaction and finalised with the response payload; attempt row (SUCCEEDED) |
| 2 | **New key, business refusal** (e.g. `INSUFFICIENT_FUNDS`) | 409 + reason | **No** journal | Refusal is a *committed outcome*: attempt row (REFUSED) + key row with refusal response; replaying later returns the **same refusal** even if balance changed — via the same replay gate (row 7); client must use a new key for a genuinely new attempt (documented) |
| 3 | **Authorisation refusal** | Single uniform **404 `ACCOUNT_NOT_FOUND`** envelope (indistinguishable from a missing account — T-020 fix in Rev 1) | **No** journal, no key row | Money tx rolled back; separate short audit tx writes the attempt with the true internal reason (AUD-002) |
| 4 | **Replay, same key + same canonical payload** | Stored response replayed (success or refusal as originally committed) — **only after the row-7 gate passes**; a failing gate returns the gate's 401/404/409 instead, never the stored body | None (original effect stands) | Row shows request hash matches; response includes `replayed: true` modifier in the envelope for UI honesty (financially identical); the gate writes nothing (no counter bump, no attempt row). **Replay is semantic (ADR-004 §1a):** same status + identical business field values (money/sequences as JSON strings, T-049) plus `replayed: true` — the stored `JSONB` body is not a byte-image of the first response (JSONB normalises key order/whitespace/number formatting); byte-identical replay was evaluated and not chosen |
| 5 | **Replay, same key + different payload** | 409 `KEY_REUSED` | **None** — key is not "reinterpreted" | Hash mismatch; original effect untouched (IDEM-002); decided from the key row alone — no account status read needed |
| 6 | **Concurrent same key** (two transactions race) | Winner: path 1/2. Loser: blocks on the uncommitted key row (Postgres unique), then reads the committed row → row-7 gate → replay with `replayed: true` | One execution total | No "PROCESSING" state exists; the DB unique row *is* the mutex (IDEM-003); the loser's gate may still refuse (e.g. the account was suspended in the meantime) — exactly two legal orders, still one execution |
| 7 | **Replay after grant revoked / account no longer `ACTIVE` / session revoked** | **Replay re-evaluation gate** (same transaction, declared lock order, evaluation only — no writes, no counter bump, no new attempt rows; the no-write vow covers the gate pass and post-claim refusals — a replay refused **pre-claim** at step 1b records the ordinary D-9 authorisation-refusal row, one insert attempted per refused call, REPLAY-AUTHZ-001): (a) *session* — the session row was re-read `FOR SHARE` before the claim (D-8 step 1): a revoked/expired session → **401 `UNAUTHENTICATED`** (a revocation is an authentication failure, never 404); (b) *grants/visibility* — the target grant rows were read `FOR SHARE` fresh at step 1b (linearised with revocation, ADR-007): grant revoked or visibility lost → the single uniform **404 `ACCOUNT_NOT_FOUND`** envelope (this refusal occurs before the key row is read and attempts one D-9 authorisation-refusal insert per refused call — key-state-independent; exactly one durable row when persistence succeeds, T-042-bounded); (c) *status* — the involved account rows (deposit destination / withdrawal source / transfer source + destination) are re-read `FOR SHARE`, ascending id, and must still be `ACTIVE` (decision 11): suspended/closed but **still viewable** → **409 `ACCOUNT_NOT_ACTIVE`** (granular for a visible destination). Stored outcome returned only when all stages pass; replay-vs-suspension has exactly two legal orders | None | Key row remains but is not honoured for a now-unauthorised actor, a revoked session, or a non-`ACTIVE` account (T-028, IDEM-006, T-048); *successful* replays are observable only via the `replayed: true` field on that replay's response envelope — **v1 records no replay-side writes** in or after the gate (no counter bump, no `IDEMPOTENT_REPLAY` audit row, no replay counter/table: `docs/adr/ADR-004-idempotency-and-refusals.md` §4, deferred to v2 with human opt-in); a gate refusal stores nothing (a pre-claim step-1b refusal attempts one ordinary D-9 authorisation-refusal insert per refused call — exactly one durable row when persistence succeeds; a failed insert is logged and never suppresses the refusal; a step-1 session 401 records none — the deliberate F-3 asymmetry) |
| 8 | **Infra failure inside the money transaction** | 500 (transport), command failed | **None** — rollback releases the key claim | Key not consumed → safe retry later; FAILED attempt best-effort row |
| 9 | **Deadlock / serialization (40P01/40001)** | Retried transparently (up to 3×) then 503 | One execution total (retry is same-transaction, same key) | Retry always: whole command, same key, claim inside the tx (CON-003) |
| 10 | **Commit succeeded, response lost** (timeout/disconnect) | Client retries with **same key** → replay (path 4) | One execution total | UI keeps the same key in the retry-safe state; shows "unknown → resolving" not "failed" (T-030, IDEM-005) |
| 11 | **Key reused across a different operation or user** | Effectively an unrelated fresh key (scoped differently) | As per rows 1–7 for that new scope | Scope prevents cross-intent collision (T-027) |

## Canonical payload & hashing

- Hash input = {operation, account ids as UUIDs, amount_minor, currency, destination id where applicable, and operation-relevant validated fields} — normalised (e.g., stripping optional unknown/non-affecting fields is **not** allowed; the hash covers everything the client sent that the API validated into the command).
- Stored as hex SHA-256. Raw payloads are **never stored** (consistent with `REFUSAL_CODES.md` §3).

## Retention & lifecycle (answering T-017/T-038)

- v1: **no expiry** and **no admin delete path**. Retention = life of the dataset. Growth accepted at demo scale; documented honest limitation.
- Replay also *requires* the caller to still be authorised for the relevant accounts **and the accounts to still be `ACTIVE`** (row 7) — the key never becomes a bypass.
